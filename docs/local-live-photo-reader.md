# Local Live Photo media reader

Independent `codex/feature-local-live-photo-reader` starts from44dbafd. It adds only a pure source/proof policy, a dedicated native reader and focused tests. Root owns fresh remote still/motion validation and viewer integration; the native PhotosUI surface is another slice. Current CI/head, MediaLibraryController, LocalMediaAssociation, existing LivePhotoPlaybackView, workflows, server/API, original files and production remain untouched.

`@MainActor LocalLivePhotoMediaReading` has two stages. motionProof(for:validateContext:) returns LocalLivePhotoMotionProof?, containing the stable complete LocalPhotoSnapshot, selected pairedVideo descriptor and LocalPhotoByteDigest. That digest is computed from complete local movie bytes and is not a remote pairing assertion. livePhoto(for:targetPixels:validateContext:) returns PHLivePhoto? using current representation, highQualityFormat and network disabled. Nil means unsupported/unavailable/changed local source; Task cancellation and caller context errors propagate. A PHLivePhoto ready for display is distinct from an AVPlayerItem.

The pure first-cut policy accepts only known finite modification version, image-Live identity, live playback style, no hasAdjustments, nil adjustmentTimestamp and exactly one original image plus one pairedVideo movie. RAW, extra/duplicate/adjusted/alternate resources, historical nonnil adjustment time and Loop/Bounce/disabled-live presentation are deliberately not guessed. Snapshot descriptors and classified resources must agree. This narrow policy does not expand no-Cloud-ID Live still matching or the ordinary checksum reader's Live exclusion.

PhotoKitLocalLivePhotoDriver reads only public metadata, validates source again before the actual request, and delegates movie bytes to the existing PhotoKitLocalResourceRequests/LocalPhotoResourceSHA1Stream. The latter hardcodes network=false, hashes progressive chunks without retaining the movie or writing/exporting it, and cancels the actual PHAssetResourceDataRequestID. Successful proof requires the complete local source, authorization, version and resources to match before/after. A cloud-only/error/empty stream yields no proof. This stage still reads the local original paired-video bytes for SHA1; it does not download or export them. Streaming remains cancellable and has no additional fixed timeout; native rendering below has a four-second deadline.

Native Live requests use PHImageManager.requestLivePhoto rather than undocumented image-as-video behavior. Existing PhotoResourceRead handles actual PHImageRequestID installation, early cancellation and one completion. Degraded results are never final; error/cancelled flags are not native success. The default4s preparation limit cancels the actual request and returns nil without cancelling its caller. Both native return and proof publication recheck the caller account/page generation and local source; cancelled/revoked work cannot become a fallback from an old account.

Integration must fresh-read the still and require exact expected id/revision/owner/IMAGE/non-trash/online/non-edited state and livePhotoVideoId equal the requested motion ID. Fresh motion must be that id, same owner, VIDEO, explicitly non-trash/online/non-edited, with valid checksum and revision. Compare proof.digest.sha1Base64 exactly to the fresh motion checksum, then revalidate local/remote pair/context after native preparation. Sequential reads are not a server-side atomic snapshot. Existing still association alone cannot prove motion identity or backup completeness. Persisted pair witness/offline semantics belong to root, not this reader.

Eleven test functions/40 parameterized cases exercise pure policy, actual reader, existing real SHA1 stream and cancellation gates using synthetic metadata/bytes/native callbacks. A34-byte movie string hashes to58be777b9bf5f3971870cc8725c828fcfc089cf2, independently confirmed with Node crypto. Cases cover unsupported source variants, wrong proof resource, changed permission/version/resources, cloud-only/errors/empty input, actual current/network/options/pixels, missing native handle, degraded timeout, cancelled-before-start, cancelled-before-ID, running cancellation and caller revocation. No real Photos library, media file, account, network or production content is accessed.

PHLivePhoto has no general public empty-success initializer. Tests do not use PHLivePhoto(), unsafe casts or a fake object as native success; native nil/error/option/cancellation tests prove only those paths. Successful real Live Photo preparation and audiovisual playback remain unverified. NAS scoped SwiftFormat0.64.5 on the three Swift files and diff checks passed. Swift compilation/runtime, native callbacks, iPhone Photos permissions/local-vs-cloud behavior and actual playback require root's separate macOS/device checks. No push or CI was triggered.

Rollback removes these isolated files and their separate host dependency together. No database/recovery migration or photo restoration is needed. A reader proof never permits backup completion, original replacement or device-space cleanup.
