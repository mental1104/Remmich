# Persistent photo backup

This branch develops backup reliability independently of search CI. `PhotoBackupView` now connects the durable journal to a serial foreground worker, cancellable PhotoKit exporter and explicit scan/resume/single-item controls. This is an **implemented, unverified slice**: NAS static checks are available, but Swift compilation, simulator execution and real PhotoKit/iCloud/media acceptance have not run. It is not yet merged into `dev` or advertised as tested backup reliability.

Opening the page only restores interrupted stages as paused and reads the saved account configuration. A scan persists selected albums, excluded albums, cloud consent and source versions without uploading; a separate confirmation starts the queue. Continue retries queued/paused/failed jobs, keeping completed/cancelled history. Single-item retry pauses other queued jobs before starting only that task. Changing selection or the iCloud toggle takes effect after an explicit scan; the upload confirmation says it uses saved scan options. Historical rows and confirmed receipts remain visible when a new scan cancels jobs that no longer qualify.

## Explicit album inclusion and exclusion

The independent `codex/feature-backup-album-exclusions` slice starts from `795fd39` and does not modify tonight's candidate or start CI. It applies exclusion before deduplication and ordering: a photo present in any excluded album is omitted even if another selected album includes it. Included and excluded collections must all be successfully refetched; a missing collection aborts before journal writes. Only currently authorized PhotoKit photos/videos are enumerated. Limited access remains limited, and changed source snapshots across included albums require a new scan. Membership changes after the saved scan do not automatically change its frozen queue.

Successful explicit scans cancel every unfinished source/version no longer eligible, retaining any motion/primary receipts and the historical row. Completed rows outside the new selection retain their completed stage. Eligible completed rows follow the existing rescan behavior: queue them again for server duplicate/receipt verification, preserving their receipts; local completion does not prove the server still retains the asset. No scan removes local originals or remote assets, and no upload starts from scanning alone.

Saved selections can outlive a deleted or inaccessible device album. The controller does not classify selections as unavailable until a current album read succeeds. Initial empty state, permission denial, cancellation and failed rereads preserve choices and provide no missing-album conclusion. A successful empty list is distinct from failure. After success, the page shows the number of missing selected/excluded album IDs and offers an explicit removal button without displaying private identifiers. Removal changes only the current page draft and marks it as requiring a new scan; it does not write SQLite, clear jobs/receipts or resume uploads. Continue and single-item retry are blocked in this draft until a successful explicit scan saves it. A separate explicit task cancellation can still save that task's cancelled state without replacing the draft. Leaving without scanning discards the unsaved draft; reopening restores the previously persisted rules and still requires explicit upload confirmation.

The first nonempty exclusion rule upgrades the journal/header to version 2. Version-1 data lacking the optional field remains readable, and a scan with no exclusions stays at version 1 until the first upgrade. Once upgraded, even explicitly clearing exclusions keeps version 2. Version 2 requires a present exclusion list and a nonempty, unique, nonempty-ID inclusion list. Older version-1-only readers reject this header instead of ignoring exclusions. Unknown future versions fail before scan mutations, migration, cold loading or hot queue operations can replace recovery data. Do not manually downgrade a version-2 header to bypass this guard.

New domain/real-SQLite tests cover exclusion precedence, overlaps, ordering/deduplication, inaccessible collections, conflicting versions, cancellation with partial receipts, completed history, cold version-2 restoration, version-1 compatibility and future/malformed headers. Real Controller fixtures additionally cover initial empty/read failures, successful empty/current catalogs, explicit draft removal, blocked resume/retry and SQLite/receipt preservation; only album enumeration and an unexpected-export sentinel are synthetic. Seven scoped Swift files pass SwiftFormat 0.64.5 and diff checks on NAS. These tests have not compiled or executed here; real PhotoKit permission transitions, removed albums, iCloud, uploads and devices remain unverified.

## Queue execution and persistence

The worker persists `exporting` before PhotoKit access, the resource stage before upload, motion identity before still upload and primary identity before server verification. Every primary, including a duplicate, is read back and checked for matching identity/owner/type/non-trash state; Live Photo also requires the actual `livePhotoVideoId` pairing. Before completion, a separate fresh GET verifies the motion's UUID/owner, VIDEO type and non-trash state while the stored stage remains `verifying`. Valid archived motion is allowed; no visibility rewrite is added. These sequential GETs are not an atomic pair snapshot or CAS and do not eliminate later concurrent changes. Network/permission/unknown receipts stop the cycle and pause remaining tasks, with no timer or automatic write replay. Local missing/changed/unsupported sources can fail individually while remaining independent tasks continue. Persisted checkpoints are never bypassed for throughput.

The motion-verification follow-up over frozen62623eb adds final-read trash/type/owner/ID rejection cases and normal/archived pairing cases. The real Controller/SQLite/URLSession takeover fixture now requires six exchanges, including distinct still/motion GETs at `verifying`, and retains its no-replay/late-response checks. NAS scoped formatting, whitespace and fixture-JSON checks run; Swift compilation/tests and real service HTTP/media acceptance have not executed. The read-only environment audit found no running isolated Immich upload service, so no production endpoint was used and no temporary service was built.

`requestData` streams resource chunks to a private file and supplies a real request ID for `cancelDataRequest`. A locked writer handles cancellation before continuation registration, cancellation before ID installation, late callbacks, write errors and one-time completion/close. Source type/modification date are rechecked before/after export. A nil PhotoKit modification date is retained as unknown; this is not a content-version proof. RAW+JPEG/unsupported combinations fail explicitly instead of being counted as complete. Temporary files are removed on completion/failure; no device originals are edited.

The account generation is checked before/after awaits, and one namespace-wide retirement barrier waits for the previous cancelled task, including its pause cleanup, before a new scan/resume can write. This also covers a second window or fast return to the same account. The management channel is reserved during a run. Authentication/route changes revoke old results; cold recovery then pauses the last persisted in-flight stage. No new account storage is created from a late backup callback.

The journal reuses the existing authenticated `MediaAccountScope` and per-account SQLite storage. It stores local PhotoKit identities/source modification versions, selected/excluded album identities, cloud-download consent, finite job stages and confirmed remote asset identities. It stores no credentials, original bytes, server error bodies or private paths. Auxiliary `photo_backup_headers` and `photo_backup_jobs` tables leave existing schema/cache versions unchanged and are removed with their account storage. Each job has a stable ID, immutable scan position and indexed stage. Upload checkpoints validate/decode/encode only that job and update its existing row; they do not scan or rewrite completed history.

`loadPhotoBackups` remains the full cold snapshot, and `savePhotoBackups` remains the full transactional explicit-scan interface. Bulk replacement also validates existing recovery data before replacing it. They are intentionally O(N) in the number of stored jobs; the upload loop must not call them or the journal's linear `update` for each stage. Individual checkpoints use the primary key, and queue selection uses `(scope,stage,position)` with `LIMIT 1`; this removes the previous full-history serialization on every transition. This is a source-level complexity change, **not a measured device throughput result**.

| Worker call | Required boundary |
| --- | --- |
| `savePhotoBackups(journal,scope:)` | First persist an explicit scan to create tasks. Existing unknown versions or corrupt recovery rows fail instead of being replaced. Await success before starting any external work. |
| `nextQueuedPhotoBackup(scope:)` | Read one queued task in the original scan order. This is not a claim/lock: the caller still owns the single-worker and account/endpoint generation checks. |
| `savePhotoBackupJob(job,scope:)` | Update an already-created ID with exactly the same source snapshot. Unknown IDs/source replacement fail; a late single-item save cannot insert a deleted task, including after the same account reauthenticates. Keep a local mutable job and await every checkpoint before the next export/network side effect. |
| `pausePhotoBackupWork(scope:)` | Atomically pause queued and in-flight rows only, retaining confirmed receipts and terminal history. It persists cleanup even if the calling Task was cancelled. |
| `recoverPhotoBackupWork(scope:)` | Pause only interrupted in-flight rows. Queued rows remain queued, but this call does not run a worker or resume uploads. |

All entry points check the authenticated namespace/header version; hot writes do not create an absent header. Bulk and single-job writes, and queue reads, honor cancellation. Stop/recovery calls intentionally remain usable from cancellation cleanup. Storage alone cannot distinguish a superseded worker using the same authenticated scope: runtime account/endpoint generation checks remain mandatory before and after awaits.

An existing version-1 `photo_backups` blob is validated and converted once in a transaction: write the complete header/ordered jobs, then delete that old row. Any decoding/version/namespace/duplicate failure rolls back and retains the original blob. A simultaneous legacy blob and row header is rejected as ambiguous rather than choosing a snapshot. Future/corrupt row headers and corrupt existing job rows also block replacement. This unpublished component has no production migration; tests use only synthetic temporary files.

| Event | Required behavior |
| --- | --- |
| Explicit album scan | Preserve scan order, deduplicate the same source, cancel unfinished older versions and recheck even previously completed items. A local receipt does not prove the server still retains that asset. |
| Upload start | Persist the next stage before any export or network side effect. Each explicit attempt increments once. |
| Live Photo | Motion receipt precedes the still upload; both identities and actual pairing verification are required before completion. No motion-only success. |
| Process interruption | Restore in-flight stages as paused with confirmed receipts retained. No upload starts merely because the journal was read. |
| Explicit resume/retry | Re-read the authorized source/version and perform server duplicate checks again; stored identities are not permission to skip validation. |
| Account/endpoint change | Cancel the old worker and revoke publication; jobs remain tied to the authenticated logical account scope. No cross-account replay. Runtime checks and retirement barrier are implemented but await Swift execution. |
| Deleted local account | Late journal writes fail rather than recreate the deleted account or overwrite another account. |
| Corrupt/future journal | Fail explicitly and preserve recovery data; do not replace it with an empty queue. |
