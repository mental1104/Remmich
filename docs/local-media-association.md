# Local media association for browsing

The independent metadata slice `codex/feature-local-media-match` is based on424a22a. Its follow-up `codex/feature-local-photo-media-reader` starts from472d8a7 and implements actual local-current image/video requests behind a narrow injectable PhotoKit boundary. These slices supply metadata candidates and a local reader for Immich browsing, enlargement and playback; media-loading entry-point integration is separate. Backup workers/journals, mutations, SQLite, server/API, workflows and tonight's candidate are untouched; association is not backup completion, original-byte identity or device-space-cleanup evidence.

## Exact official metadata

`LocalMediaMobileMetadata` decodes `iCloudId`, `createdAt`, `adjustmentTime`, `latitude` and `longitude`. The Swift property is `cloudId`; the wire key is exactly `iCloudId`. IDs remain complete opaque strings; do not interpret the internal suffix as SHA1. Empty/whitespace/known incomplete trailing-colon IDs cannot match. Failed or missing mappings remain unknown.

The official `mobile/lib/domain/models/asset/asset_metadata.model.dart` custom toJson omits nil entries. Only those four known nullable fields therefore permit missing/null equivalence. Nonempty bad dates, wrong types, nonfinite or out-of-range coordinate strings throw rather than becoming nil. Remote fractional time stays precise; only local creation/adjustment times follow the official native bridge's truncation toward zero to whole Unix seconds. Coordinates and optional values compare exactly. A missing native creation time cannot reproduce the official client's current-time fallback, so no time is invented.

The reference is `mobile/lib/infrastructure/repositories/local_asset.repository.dart:222`: the official client reconciles checksums using equal Cloud ID, creation/adjustment time and coordinates before computing missing hashes. This slice uses that identity/version relationship only to find a display candidate. Duplicate candidates, including duplicate UUID records, are ambiguous. `LocalMediaMatch.resolve(expected:snapshot:candidates:)` rejects changed local observations; Photos edits are allowed when their public adjustment time is known and equal. Live Photo/RAW+JPEG objects can associate for Photos current rendering, without proving their original resources or remote motion pairing were backed up.

`LocalMediaRemoteCandidate` holds only asset UUID and decoded metadata. Root integration must fresh-read owner/type/version/server edit state before selecting local display. Immich nondestructive edits may change display without changing uploaded mobile metadata; until the local renderer applies that edit chain, server-edited display must retain the remote edited-media path.

## Public PhotoKit reader

`PhotoKitLocalPhotoMetadataReader.snapshots(for:validateContext:)` accepts at most64 nonempty distinct local IDs, preserving request order. It reads authorized PHAsset metadata and PHAssetResource descriptions, performs Cloud ID mapping off the main executor, then re-reads the metadata before returning. Changed metadata, cancellation or revoked account/page generation cannot publish old associations. System mapping has no cancellation handle; cancelled results are discarded after it returns. Only Sendable values cross the executor boundary, with no PHAsset objects.

Captured fields are local identity/modification time, creation/adjustment time, hasAdjustments, coordinates, pixels/duration/subtypes and resource type/filename/UTI/dimensions. Resource ordering is canonical and duplicates remain visible. These are structure/version observations, not a hash. Asset dimensions describe current edited content. No private KVC, isCurrent, fileSize, locallyAvailable or official-device-ID reconstruction is used. Required APIs fit minimum26.6: resource dimensions are public from16, hasAdjustments from15 and adjustmentTimestamp from18. The27-only optional dataSize is unused. The old macOS-only PHCloudIdentifier.notFound constant is not used with iOS's Result mapping.

This reader never calls requestImage, requestData, media export or image/video loaders. Cloud ID mapping can be expensive and may involve system metadata networking; this is not a promise of zero iCloud network activity. It does not request original photo/video bytes.

## Display integration boundary

`@MainActor LocalPhotoMediaReading` exposes image(for:targetPixels:validateContext:) and playerItem(for:validateContext:), returning UIImage? and AVPlayerItem? respectively. Both accept the matched LocalPhotoIdentity, including its expected modificationDate. The default PhotoKitLocalPhotoMediaReader uses public PHImageManager requestImage for current photos/posters and requestPlayerItem(forVideo:) for ordinary video. Both explicitly set version.current and isNetworkAccessAllowed=false. Image requests retain the caller's target pixels with aspectFit/highQualityFormat; a degraded result is never accepted as the final image. Target pixels remain bounded by the integrating pipeline.

The reader reuses the existing PhotoResourceRead gate to install/cancel the actual PHImageRequestID, including cancellation before the system call returns its ID. Repeated/late callbacks cannot finish a read twice. A four-second deadline cancels a hung native request and returns nil; a cancelled caller still throws CancellationError. Known modification version, source identity, public adjustment time/state, pixel size, duration, subtypes and current authorization are checked before and after the request. Changed or unavailable sources return nil. Account/page validation runs before/after observations and after awaiting: revoked publication rights throw rather than allowing old-account remote fallback. The reader neither prompts for authorization nor starts original-data requests/exports.

Nil explicitly means current content was not locally readable, allowing the current caller to use Immich without silently downloading an iCloud original. A Live Photo still uses requestImage; its image PHAsset is rejected by the ordinary video entry. Live Photo motion/sound remains a separate unimplemented requestLivePhoto path. AVPlayerItem may represent Photos compositions, so integration must not assume AVURLAsset. Immich's server-edit gate and actual MediaLibraryController local-first wiring remain separate root integration work. Real PhotoKit callbacks, cloud-only fallback, permission changes and device playback remain unverified.

## Validation and rollback

Metadata pure-domain and actual-reader tests cover exact tuple/null/version/current-edit rules, duplicate ambiguity, failed mappings, strict wire values,64-item bounds, invalid identities, changed resources and cancellation/revocation during a real held await. The media-adapter follow-up adds13 test functions/34 parameterized cases: actual options/current/network flags, image/video/Live Photo still routing, unchanged Photos adjustments, missing native request handles, rejected degraded/failure results, before/after source and permission changes, request-ID installation races, running cancellation, repeated late callbacks, bounded timeout and account revocation. Only the native request/metadata boundary is synthetic; the product gate and orchestration execute unchanged. UIImage fixtures are generated color pixels and AVPlayerItem uses an empty composition, with no disk/media/network access.

NAS scoped SwiftFormat0.64.5 and diff checks pass for both new adapter Swift files. The earlier metadata slice also passed fixed-JSON syntax checks. Swift compilation/tests and actual Photos/iCloud/device behavior have not run. No private media, real account, service mutation, production write, push or CI execution was used.
