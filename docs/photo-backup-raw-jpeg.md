# RAW+JPEG original backup

Independent branch `codex/feature-backup-raw-jpeg` starts from `59cd836`. Model/storage boundary775c6fc is followed by actual PhotoKit export, Worker and cold-recovery wiring. This is **implemented, not yet compiled or executed in Swift**. No CI, push, production/private-media mutation or official API/SDK change is included.

The accepted group is one original `.photo` and one `.alternatePhoto`, publicly classified by UTI as one RAW and one JPEG, with positive dimensions and names. Their array order and the association of RAW with `.photo` are irrelevant. Adjustments, unknown/extra resources and absent source modification versions cannot become complete groups. The source snapshot stores both canonical descriptors. Single-image, video and Live Photo behavior remains separate.

`PhotoBackupJob` adds distinct `rawReceipt` and `jpegReceipt` (remote UUID, actual-byte canonical Base64 SHA1, duplicate status), without repurposing Live Photo's motion/primary fields. Each component is independently re-exported/checked on every explicit attempt; retained receipts are recovery history, not permission to skip server validation. Both distinct assets with different SHA1 values must be verified before one logical task completes. Cold completed-state validation requires the same conditions as the completion method; corrupt same-checksum/different-UUID JSON cannot claim completion.

Scanning only obtains public resource metadata, never media bytes. The default exporter rejects Photos adjustments, missing/changed versions, unknown/extra members and mismatched full descriptions; role selection never uses array order, filename extensions or private `isCurrent` KVC. The original resource manager streams RAW then JPEG with the current explicit iCloud consent, preserving cancellation of its actual request IDs. After both reads it refetches and compares the complete source/creation/modification/favorite observation. One failure removes all temporary output; it never changes device originals.

Before upload the Worker persists the existing uploading stage. It computes each actual file's nonempty streaming SHA1, calls the unchanged uploader (official SHA1 precheck and disk multipart), then fresh-reads and checks the returned UUID/owner/IMAGE/non-trash/checksum and **explicit `isOffline=false`**. Only then does it persist that component receipt. After both components it persists verifying, independently reads both again and confirms one completed logical task. SHA1 is checked on both created and duplicate paths; missing checksum or unknown/true offline state is unconfirmed. The optional DTO field remains unknown for older responses, without changing ordinary/Live verification semantics. The reads are sequential, not an atomic server snapshot/CAS or a promise against later deletion. A duplicate JPEG with an existing Live motion link remains valid original bytes and is not modified/unlinked. Both components must be duplicates to increment the logical duplicate count.

On second-component failure, cancellation or account retirement, any already-verified first receipt remains in SQLite and no partial group counts as success. A fresh SQLite connection restores interrupted work to paused; explicit resume re-exports both originals and repeats both official duplicate checks, rather than trusting a stored UUID. Existing ordinary/Live branches keep their motion-first checkpoints and final pair/still/motion reads. No automatic Stack, device-ID scheme, upload rollback or remote delete is introduced. Remmich's existing uploader does not send `deviceAssetId/deviceId`; its actual existing idempotence boundary is file SHA1 plus confirmed remote identity.

The first scan containing a RAW+JPEG source atomically upgrades journal/header to version3 with `rawJPEGVersion=1` and an explicit exclusion list. Old v1/v2 remain readable. Existing unknown-version3 documents without the marker remain invalid. Version3 never silently downgrades on later scans; bulk/hot SQLite writes reject incompatible replacement. A pre-v3 reader rejects the header, rather than ignoring the second still and completing a partial backup. Existing account database schema is unchanged.
