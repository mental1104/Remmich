## 无导入的服务端匹配（当前改动）

没有SQLite时先读取Photos公开元数据和完整云标识，按官方元组关联当前账号的完整服务端mobile-app及本客户端来源流；一项候选必须唯一且当前资源拥有者、类型、版本、在线/非回收站/未编辑状态明确。本机原片是否下载不影响元数据匹配，不使用原片导出或哈希来完成这条路径。

完成整批分类并重读本机观察后，按64项批次经已有PUT /assets/metadata写独立remmich-icloud-match，包含version=1、method=icloud-id、iCloudId和byteVerified=false。只修改这一自有元数据key，不覆盖mobile-app、资产内容或上传回执。回复必须逐UUID完整确认原值；失败/取消不发布本地已匹配，不启动上传。服务器是先前已有能力，不需要部署或修改API。

移动端持久状态existing显示“已匹配（服务器已有）”，不会因进入后台或自动扫描重排为未尝试尾队列。不增加上传成功数、次数或伪造字节/Live/RAW完整回执；Live及RAW的这种记录仅表达逻辑源身份匹配，不能作为动态/双原图完整性或清理手机的依据。

未匹配但Photos源可读取、版本当前且没有未知尝试的新项目，继续进入既有原片导出→实际SHA1→Immich查重→仅未命中时上传→fresh确认。iCloud下载仍服从用户选择；缺失/变化/歧义或不明远端状态保留待核查。明确恢复的任务重新查重，未知尝试不会自动重发。SQLite仍可选导入，导入历史原有保守政策保留。

原片已fresh确认相同checksum及在线身份后，将实际SHA1与本轮公开Photos元组保存到每云ID独立的remmich-backup-icloud-<SHA256>元数据，值为version=1、method=sha1、byteVerified=true、checksum和metadata。不同云ID不覆盖彼此或官方mobile-app；第二台设备可从完整流读到此来源，再按相同元组/fresh资产完成ID匹配。只通过ID匹配的新观察仍单独记录false，不提升为本次字节验证。原片成功而来源PUT失败时保留回执并显示未确认，明确恢复先查重，避免再次提交媒体。

## 导入缓存的既有接续行为

- 相簿枚举、资源描述与去重排序离开 UI 主线程；每项枚举检查取消，运行状态先发布。任务列表分页展示，恢复摘要只在队列更新时计算。
- 可选导入官方 Immich SQLite 加速缓存接续。Importer 只读固定标识、缓存 checksum 和修改时间，要求当前账号一致；保留缺失项，不修改导出文件。当前支持 NAS 已有精简导出的四字段本机表与账号表。
- 手动继续、前台自动和系统后台都在唯一 Coordinator 与管理通道内完成整批核查，再把完整源版本许可交给 Worker。Worker 在原片导出之前拒绝许可外的任何源。
- 同手机优先按本机 ID 索引读取历史；找不到时才有限批量读取公开 Photos 元数据和完整 iCloud ID。历史 checksum 走官方 `bulk-upload-check`，每批最多 64 项；缓存摘要与实际读取字节证明是两种类型。
- 已核对官方iOS `PHAssetExtensions.swift`：`updatedAt`来自 `Int64(modificationDate.timeIntervalSince1970)`，只有整秒精度。缓存查询按同样精度选择候选，不能把同秒命中当作当前原片逐字节证明，因此已有项目记为已匹配、不生成上传成功回执。
- 历史版本不一致、缺摘要、歧义、服务器未命中或回收站项目保持待核查；不为补哈希下载原片。已有主体记为已匹配并保留记录，不伪造完整 Live Photo、RAW+JPEG 或上传成功回执。
- Live Photo/RAW+JPEG只有主体命中时进入待核查。跳过与待核查都计入处理进度，但不计入新上传完成数。已尝试的新源只通过明确单项核查或已授权且验证过的网络恢复重新核查，仍须满足导入之后的时间/版本及完整远端元数据条件。
- 新拍摄和修改时间都晚于导入时刻、没有历史关联且官方完整同步元数据没有当前关联的源，才可获得新上传许可。查询失败、增量检查点、部分流或账号/端点变化都停止，不使用部分许可。
- 导入前新增但不在历史里的照片需要单独核查。未完成全量元数据读取时不把未知当作新照片。没有导入记录时使用上面的服务端匹配路径，不自动将全库重新上传。
- 已安装Mac候选的 `existing` 与 `historyNeedsReview` 队列值保留读取兼容；不会把已有候选当作完整上传回执，不清空旧队列。未知未来格式仍拒绝。接续导入只使用本版明确导入的数据；原精简SQLite可以重复选择，原文件保持不变。
