# Saved-search lifecycle validation

This follow-up starts at PR7 head `6ed6568`. It adds five Swift Testing functions (seven cases after account/endpoint parameterization) for existing saved-search behavior. No server, API, schema, workflow, production deployment or saved-photo behavior changes.

`LibraryManagementController` accepts an internal optional `configurationFactory`, defaulting to `nil`. Existing production construction remains identical: a normal `LibraryMutationClient` creates its original ephemeral session. Tests provide a fresh session configuration with a local `URLProtocol`. All HTTP requests still traverse the real manager's `perform`, client path construction, Bearer authentication, JSON encoding/decoding, exact status validation and cancellation. Every test has exclusive random hosts; the protocol intercepts every request in those sessions and fails an unregistered host, so no real network is used. It is never registered globally.

| Case | Independent assertions |
| --- | --- |
| Conflict and reload | Real GET succeeds, real POST receives409, Store returnsfalse and clears freshness. A second create cannot send another request. A successful explicit GET restores write permission; a subsequent explicit POST201 installs the confirmed record. Both POST bodies and all request counts are checked. |
| Rename | The initially displayed record is stale. A second real GET supplies newer full conditions, including reference/person/device/media/EXIF fields and explicit null rating/tags. PATCH must contain those complete newer conditions and the new name. |
| Replace | A second real GET returns a name changed elsewhere. PATCH must preserve that latest name while replacing conditions with the user's complete current query, including null states and extension filters. |
| Obsolete Store load: account / endpoint | A real authenticated GET reaches a response gate. Production `configure` cancels the old client; the Store is invalidated as in the Panel's generation listener. The current context loads its own record before the old planned200 is released. Old work cannot overwrite the new list or change its freshness/error/busy state. |
| Decoded success: account / endpoint | A real POST201 is already decoded by `LibraryMutationClient`. Only then does a handshake gate delay the operation's return. Context changes and the current Store loads before the success value is released; the real `perform` must reject it as `changedAccount`. This independently verifies the generation guard rather than relying on URLSession cancellation. |

The cancellation fixture honors `stopLoading`; it does not force obsolete URLSession bytes into application state. The post-decode case deliberately tests the different boundary where HTTP has already succeeded. No sleeps, real identities, credential stores, production connections, media files or photo writes are used. The fixed response script implements no saved-search business logic; production Store/manager/client code determines success, failure, freshness, rename/replace composition and publication.
