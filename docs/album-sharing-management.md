# Shared album member management

Independent `codex/feature-album-sharing` starts from `c20e300`, preserving the date slice and leaving Saved UI, backup candidates, workflows and production alone. Entry: **Albums → Album management → 成员与共享权限**. The separate page reads all visible albums, including viewer-only shares, and their full ordered `albumUsers[{user,role}]`; it does not use the legacy owner projection for authorization. The separate `df816a5` compatibility fix is required for the older management page's existing `ManagedAlbum` reads when official responses omit `ownerId`.

The parent checkout's inspected server is `7653378`; album controllers/access match its official `main`. Official paths are unchanged:

| Intent | Request / expected response | Boundary |
| --- | --- | --- |
| Read | GET `/albums`, `/albums/:id`, `/users`, exactly200 | Existing server accounts only. Full ordered members; no email invite/accept endpoint. |
| Add one existing user | PUT `/albums/:id/users`, `{albumUsers:[{userId,role}]}`, exactly200 album | One member only; the server's multi-add loop can partially write on a later failure. Direct owner addition is forbidden. |
| Change one role | PUT `/albums/:id/user/:userId`, `{role}`, exactly204 | Protected first member cannot change role. |
| Remove / leave | DELETE `/albums/:id/user/:userId`, exactly204 | Explicit UUID, not deprecated `me`; last owner cannot be removed. |

Server `AlbumShare` permits owner **or editor**. Owner membership can exist in multiple rows, so permission is derived from the authenticated member's role rather than one `ownerId`. Viewer can inspect/legally leave itself. Unknown roles remain visible but all writes are disabled. The UI offers editor/viewer roles, matching the official Web's selectable roles; it does not add/promote owner. Existing non-first owners are still correctly recognized for management, legal removal/exit and server-allowed demotion. Official Web shows owner/editor/viewer but locks owner rows; the inspected mobile sharing UI adds existing user IDs with default editor and exposes owner-oriented removal/self-leave, without role editing in that path. No official mobile source or SDK is modified.

The actual Store obtains fresh list/detail/account candidates, creates one explicit plan containing album/member/desired role and baseline, then consumes that plan once. Inside the real manager's reserved operation it reads detail again, compares the complete modeled membership, rechecks permission, sends exactly one write and fresh-reads the result. Add/change/remove-other require exactly the intended role-map change with no extra membership changes. Self-leave requires a successful fresh visible-album list that actually omits the album; access-denied details are not exit confirmation. This is sequential optimistic checking, not server CAS or a guarantee against later concurrent changes.

Page, account, endpoint and Task generations guard each await. Leaving/backgrounding invalidates the page and cancels the actual read/write; a sent but unconfirmed same-account write invalidates other readers once. Errors, wrong success codes, cancellation and post-read mismatch leave the page requiring an explicit reload; there is no automatic write replay. Confirmations name the album/member/target role; user names stay in current-account UI, not logs. No photo deletion, album deletion, original replacement, invitation, Stack or ownership-transfer scheme is introduced.
