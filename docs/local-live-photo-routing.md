# Local Live Photo media entry

Independent `codex/feature-local-live-photo-routing` starts fromf92b1e8, with the pure remote-pair model, native PhotosUI surface and local proof/reader already present. This slice changes only MediaLibraryController dependency/helper hunks and adds focused routing tests plus documentation. Root owns LivePhotoPlaybackView/AssetViewerView host selection; existing/current CI and workflows are untouched.

The new localLivePhoto(stillAssetID:revision:motionAssetID:targetPixels:) returns PHLivePhoto? after this sequence: require the current enabled same-revision Live still association; fresh-read still and motion; verify LocalLivePhotoRemotePair for exact owner/link/type/status/revision/checksum; read the local motion proof and require identical local identity plus exact paired-video SHA1; prepare native current content at <=4096 pixels per side; after a nonnil native result fresh-read both remote details again and require pair equality. Only then record devicePhotos origin and return the native object. Sequential reads do not provide a server-side atomic transaction.

Task/scope/management generation is checked after every await and in the error path. Current association equality is checked separately, so disabled matching or revoked Photos permissions becomes a normal local miss and allows the same account's caller fallback; cancelled/changed account/route work throws CancellationError and cannot authorize old-account fallback. A plain unsupported/unknown/metadata/local-read failure returns nil. This helper never calls Nuke loading, motion download, export, upload or device deletion. The caller still owns the existing remote motion path.

Initializer parameters are appended after the existing profileImageSession: localLivePhotoReader defaults to PhotoKitLocalLivePhotoMediaReader, and optional remote defaults to the current authenticated management client. The override is instance-scoped for real-helper tests; no global networking behavior changes. The Saved Photos initializer sets defaults and its helper path immediately returns nil, preserving that library's existing behavior. Production cold-offline local motion cannot fresh-check a remote pair without a client, so this first entry does not advertise new offline Live playback from a stored still association alone.

Ten test functions/50 parameterized cases execute the real Media helper and JSON restoration with synthetic inventory, fresh-detail and PhotoKit protocol boundaries. They cover verified motion reaching native, missing/invalid link and unsafe fresh fields, wrong proof identity/version/hash, old indexed version/ordinary-photo/malformed motion ID, first/second fresh failure, proof/native errors, pre-cancellation, retirement at all four awaits by cancellation/account/route/preference/permission, a late error after account/route change, and Saved Photos isolation. Nuke requests are recorded and remain zero; profile URLSession, exports and persistence are isolated, and the helper has no remote-media call. No real Photos/account/media/network/production content is used.

Native tests deliberately return nil. No PHLivePhoto(), unsafe cast or fake successful native object is created. Consequently the successful native return, subsequent two real detail reads and devicePhotos source publication are source-reviewed but not runtime-proven by these tests. Actual native preparation/playback and host selection remain separate acceptance work. NAS SwiftFormat0.64.5 on the two changed Swift files and diff checks pass; Swift compilation/tests and device behavior remain unverified. There was no push, CI trigger, server/API change or production operation.

Rollback reverts this helper/dependency/test slice together with any host call to its interface. No photo data, server database or recovery format migration is involved. Ordinary photos/videos, explicit originals and existing Saved Photos paths are unchanged.
